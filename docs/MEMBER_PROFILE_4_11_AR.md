# ملف العضو وطلبات التصحيح — 4.11.0

المرجع: موافقة المالك في 19 أكتوبر 2026 على إتاحة اختيار المدير بين تحديث التطبيق وحده أو السجل الأصلي. لا يغير هذا التفويض صلاحيات هوية قراءة العضوية الحالية، ولا يفوض تعديل كود أو Auth أو قواعد أو IAM مشروع MyNekaba من سكربت النشر.

## السلوك

الملف للعرض فقط، ويعرض بيانات العضوية والعمل والتواصل الموجودة، مع بدائل واضحة للبيانات الناقصة وتوقيت القاهرة للدخول. تشمل قائمة التصحيح الاسم، الكود الوظيفي، رقم العضوية وطبيعتها وحالتها، الهواتف والبريد والعنوان، الوظيفة ومكان العمل والدرجة والمؤهل، الفرع النقابي وحالة الاشتراك والتواريخ الأساسية المسجلة والنوع والحالة الاجتماعية. لا تُعرض الهوية القومية الكاملة أو المرفقات أو الحقول المالية أو كلمات المرور أو أي حقول غير معروفة.

يعرض موقف العمل كما هو مسجل؛ لا يستنتج استحقاقًا طبيًا أو حالة عمل من السن. حالة الوفاة بصيغها المعروفة أو تاريخ وفاة صحيح غير مستقبلي تمنع الدخول، حتى مع سياسة `all_registered`. تتكرر المراجعة في الطلبات المحمية واستعادة الجلسة، مع فحص دوري كل دقيقة للعضو أثناء ظهور الصفحة. لا يمكن ضمان مسح شاشة مفتوحة فورًا عند انقطاع الإنترنت. حظر المصدر يعلو على أي بديل محلي؛ كما يُحترم حظر الوفاة المعتمد محليًا.

## طلب التصحيح

النموذج يعرض الحقول الأساسية الحالية، ويخزن التغييرات فقط بعد تأكيد العضو ومعاينتها. اللقطة المرجعية موقعة خادميًا؛ تغير البيانات بعد فتح النموذج يفرض إعادة التحميل. طلب واحد قيد المراجعة لكل عضو، ومعرف إرسال يمنع التكرار. يمكن إلغاء الطلب المعلق، ولا يمكن إلغاء تحديث أصلي بدأ تطبيقه.

المدير يحدد الحقول المقبولة، كليًا أو جزئيًا، أو يرفضها كلها. القرار مرقم ويمنع مراجعتين متعارضتين أو تكرار الأثر عند إعادة الطلب. يصل إشعار خاص بصاحب الطلب، ولا ينشأ خبر عام. قراءة الإشعار لا تخول الاطلاع على إشعارات الآخرين. تحديث القائمة الدوري يستخدم رقم نسخة؛ لا يعيد قراءة كامل الإشعارات إذا لم تتغير.

### التطبيق فقط — الخيار الافتراضي

تحفظ القيم البديلة في Medical مع قيمة المصدر وقت الطلب. إذا تغير المصدر لاحقًا إلى قيمة أخرى، تُعرض قيمة المصدر الأحدث. يظهر وسم «معتمد في رعايتي فقط»، ويذكر الإشعار أن سجل النقابة لم يتغير. تظل مطابقة الدخول بكود وموبايل المصدر الأصليين؛ تغييرهما محليًا لا يغير تسجيل الدخول.

### تحديث السجل الأصلي — اتصال اختياري منفصل

يتاح فقط عند تكوين `MYNEKABA_PROFILE_WRITER_ACCOUNT` بهوية كتابة منفصلة داخل مشروع المصدر، تختلف عن هوية القراءة ومشروع Medical. القيمة غير السرية وحدها لا تثبت أن الصلاحيات الخارجية تعمل. الإعداد غير الصحيح يعطل هذا الخيار دون تعطيل دخول بقية التطبيق.

قبل الكتابة يُثبت Medical وجهة القرار وحقوله في حالة `applying`. الكاتب المنفصل يقرأ الحقول اللازمة فقط في معاملة Firestore، ويتأكد أن **كل** حقل مختار ما زال مساويًا للأصل أو للقيمة المطلوبة. التعارض يوقف المجموعة كلها. تُستخدم `update` لسجل `employees` موجود فقط: لا إنشاء ولا حذف ولا تعديل حقول أخرى أو Auth أو IAM أو قواعد المصدر. المعاملة تعيد المحاولة بأمان؛ القيم المطبقة سابقًا لا تُكتب مجددًا.

لا توجد معاملة ذرية مشتركة بين المشروعين؛ لذلك يُحفظ قصد ثابت ثم يُستكمل القرار في Medical بعد تأكيد الكتابة. فشل الاتصال يترك الطلب قيد التطبيق ويتيح إعادة المحاولة بنفس الاختيارات. لا يتحول القرار إلى حفظ محلي تلقائيًا، ولا يرسل إشعار تحديث المصدر قبل التأكيد. إذا تغير المصدر مجددًا أثناء تعطل العملية، يتوقف الاستكمال للمراجعة بدل الكتابة فوقه؛ قد يتطلب ذلك تسوية إدارية منفصلة.

## تفعيل اتصال الكتابة عند الحاجة

هذا الجزء لم يُفعّل بمجرد نشر الواجهة، ولا يغيره سكربت Medical تلقائيًا:

1. إنشاء هوية خدمة مستقلة في `nekaba2026` لتحديث ملفات الأعضاء، دون استخدام `medical-membership-reader` ودون تنزيل مفاتيح JSON.
2. منحها أقل صلاحيات Firestore اللازمة لقراءة وتحديث سجلات الأعضاء القائمة وتنفيذ المعاملات. لا تستخدم Owner أو Editor. صلاحيات IAM العامة لا تقيد الحقول؛ قائمة الحقول والمعاملة داخل الكاتب تمنع التوسع في هذا المسار. راجع نطاق قاعدة البيانات والصلاحيات مع مسؤول Google Cloud.
3. تمكين IAM Service Account Credentials API عند الحاجة، والسماح **لهوية تشغيل Medical الفعلية** بانتحال هوية الكاتب عبر `Service Account Token Creator` على حساب الكاتب نفسه، دون توسيع الصلاحية للمشروع كله. تحقق من هوية تشغيل Cloud Run قبل المنح.
4. إضافة البريد الخاص بالكاتب فقط إلى `MYNEKABA_PROFILE_WRITER_ACCOUNT` بملف `functions/.env.we-medical-dakahlia` المحلي المتجاهل من Git، أو متغير المستودع المقابل عند تفعيل النشر الآلي. لا تلصق بيانات أعضاء أو أسرار في المستودع أو المحادثة.
5. إعادة نشر Medical واختبار الربط أولًا بسجل اختبار مصرح به، وفحص موافقة جزئية وإعادة محاولة وتعارض. وجود اسم الحساب في الإعداد يجعل الخيار متاحًا، ولكنه لا يثبت نجاح التفويض قبل هذا الاختبار.

هذه الخطوات تحتاج جلسة Google Cloud مخولة؛ لم تُنفذ من بيئة التطوير التي لا تملك هوية نشر Google. لا تتطلب حفظ مفتاح كتابة طويل العمر في Secret Manager؛ يستخدم Medical رمز انتحال قصير العمر بنطاق datastore.

## النشر والتحقق

من Cloud Shell داخل نسخة المستودع المهيأة سابقًا:

```bash
cd ~/cloudshell_open/Medical
git pull --ff-only
bash scripts/deploy-medical.sh --existing-config
```

يحفظ السكربت هوية الكاتب الاختيارية الموجودة دون تغيير IAM أو المصدر، ويتحقق من قدرة `profile-management-v1` بعد النشر. ثم يمكن تشغيل:

```bash
node scripts/check-live.mjs --require-profile-management --rayati
```

هذه فحوص صحة ومصادقة عامة فقط؛ لا تقرأ ملفات أعضاء حقيقية. اختبارات الوحدة والمتصفح ومحاكي Firestore تستخدم بيانات مصطنعة. نشر Vercel لا ينشر Firebase ولا يفعّل هوية الكاتب.

## حدود التشغيل الحالية

آخر 50 طلبًا وإشعارًا لكل عضو متاحة من فهرسه، وآخر 100 طلب في قائمة المدير؛ المستندات الأقدم لا تحذف تلقائيًا. إضافة ترقيم صفحات وسياسة احتفاظ معتمدة مطلوبة قبل توسع كبير. الطلبات والتعديلات بيانات شخصية محمية داخل Medical، وقواعد العميل ترفض الوصول المباشر؛ لا تصدرها كتقرير عام. لا توجد سياسة حذف تلقائي لهذه الطلبات في هذا الإصدار.
