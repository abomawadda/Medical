| أدوار المتابعة | أدوار المتابعة | أدوار وقنوات يحددها المدير للتجربة؛ لا حسابات أو صلاحيات أو رسائل لأشخاص |

المعاينة المحدَّثة `service_planning` لها مراجعة **`p4-p5-20261021-2`** في الواجهة والخادم. لا ترث اعتماد المراجعة الأولى. بقية المعاينات تحتفظ بمراجعاتها السابقة. لوحة الجاهزية للقراءة فقط ومراجعتها `p0-readiness-20261021-1`؛ لا تحفظ قرار تعميم ولا تفعّل أي ميزة.

## السريان وسلامة المرجع

- تُحسب التواريخ وفق يوم القاهرة في الخادم. مصدر المسودة لا يحمل تاريخ مراجعة مستقبليًا، وبداية السريان والمراجعة التالية تواريخ صحيحة. نهاية السريان اختيارية إن لم يحددها المصدر، ولا يجوز أن تسبق البداية. مراجعة المصدر التالية لا تسبق بداية السريان أو تاريخ مراجعة المصدر.
- «جاهزة للمراجعة الخاصة» تتطلب مصدرًا أو مرجعه وتاريخه والجهة المصدرة والمسؤول والخطوات، ثم بداية السريان والمراجعة التالية وقناة تقديم. هذه جاهزية تجربة فقط، ولا تؤكد الإدارة سياسة الشركة من اكتمال الحقول وحده.
- لا يبدأ مثال جديد بإجراء لم يبدأ سريانه أو انتهى أو تجاوز تاريخ مراجعته أو نقصت بيانات سريانه. يوم النهاية أو المراجعة نفسه داخل الفترة؛ اليوم التالي يوقف إنشاء أمثلة جديدة به.
- لا تمحى مسودات 4.16 أو حالاتها. تظل المسودة القديمة قابلة للعرض والأرشفة، ويظهر نقص السريان دون تخمينه. إن استُخدمت في مثال تُنسخ لمراجعة جديدة لاستكمالها؛ لا يتبدل مرجع المثال القديم.
- يحتفظ المثال الجديد بنسخة مصدر الإجراء وخطواته ومتطلباته وقناته وسريانه التي بدأ بها. تغيير دور أو إنشاء مراجعة إجراء جديدة لا يبدل هذا المرجع. تظل المسودة المستخدمة محمية من تعديل المحتوى؛ الأرشفة مسموحة ولا تحذف الحالة. رد العملية المكرر يبقى معرفًا حتى بعد أرشفة المسودة.
- يكتشف نموذج التحرير تغير مراجعة المسودة منذ فتحها؛ لا يستبدلها تلقائيًا. يمكن نسخ النص الحالي في النموذج إلى مسودة جديدة بدل فقده. لا يوجد ترحيل مدمر أو كتابة إلى MyNekaba.

## الإسناد والاستكمال والإلغاء

1. ينشئ المدير مثالًا من مسودة سارية فقط؛ لا اسم عضو أو تشخيص أو ملف.
2. يحدد دور متابعة من الأدوار التي سجلها وتاريخًا غير سابق لليوم. هذا تاريخ تذكير إداري، وليس موعد كشف أو مهلة تعاقدية. لا تُنشأ مهام مجدولة أو رسائل تلقائية.
3. قبل الفحص أو الاستكمال أو إنهاء الاختبار يلزم الإسناد. يمكن رفض المثال أو إلغاؤه دون إسناد، ولا يمكن تخطي الفحص إلى الإنهاء.
4. سبب الاستكمال من قائمة: متطلبات، أو مصدر، أو قناة تقديم، أو انتظار رد الجهة كمحاكاة. عند اختيار المتطلبات تُحدد عناصر من القائمة المحفوظة مع المثال، دون أسماء ملفات أو مرفقات أو نص صحي. لا تُرسل القائمة للعضو.
5. الحالات النهائية انتهاء الاختبار أو الاستبعاد أو الإلغاء؛ لا يعاد فتحها أو إسنادها. إلغاء مثال موعد لا يرسل إلغاءً إلى جهة ولا يضمن استردادًا أو موعدًا بديلًا.
6. الدور المسند وقناته يُحفظان كلقطة؛ تعديل تعريف الدور لا يغير أمثلة سابقة. إعادة الإسناد صريحة ولها سجل. لا يحذف الدور ما دامت له أمثلة مفتوحة؛ إزالة دور بعد إغلاقها لا تمحو السجل.

فرز الطلبات حسب الحالة والنوع والشبكة والدور وتاريخ المتابعة، مع زر مسح التصفية. «تجاوز تاريخ المتابعة» يعني مثالًا مفتوحًا مر تاريخ متابعته بتوقيت القاهرة؛ ليس مخالفة لاتفاق مستوى خدمة غير محدد. جميع الحالات والتذكيرات تخص مساحة المدير الخاصة.

## لوحة المراحل والتقارير

- GET `/v1/admin/lab/readiness` يتحقق من المدير الحي ويعيد مراحل P0–P6 ومراجعاتها وتبعياتها وعدادات المعمل. يعاد `memberEnabled:false` و`releaseSupported:false` و`bookingConnected:false` دائمًا.
- العدادات من مساحة حساب المدير الحالي، عدا بلاغات P2 فهي أمثلة المعمل الإداري المشتركة وفق تصميمها السابق. لا تصدر اللوحة نصوص الإجراءات أو التعليقات أو ملاحظات مراجعة التصميم أو أدوار المتابعة أو معرفات حسابات الأعضاء.
- إيقاف معاينة يحجب أدلتها العددية في تقرير مرحلتها. لا يتحول اعتماد تصميم قديم إلى اعتماد مراجعة جديدة. تظل تبعيات الحجز الفعلي ظاهرة مهما اكتملت أمثلة المواعيد.
- الأعداد لقطة عند التحميل أو «تحديث الجاهزية». فحص الحالة كل 20 ثانية وعند العودة للتبويب يستخدم `?status=1`؛ لا يعيد تنزيل الدليل أو الإحصاءات أو مساحة الطلبات ولا يجدد جلسة المدير. تغير قرارات المعاينات يحدث التقرير، وفقد الصلاحية أو الاتصال يزيل المحتوى.
- تقرير المراحل وملخص الطلبات تنزيلان محليان خاصان بالإدارة، بأعداد وحالات وتبعيات فقط. لا إرسال خارجي أو نشر للأعضاء ولا أرقام نجاح أو رضا أو نتائج علاجية مفترضة.
- عند اختلاف إصدار إحدى المعاينات بين الواجهة والخدمة يتعطل فتحها ومراجعتها فقط مع تنبيه؛ تبقى المعاينات المتوافقة متاحة. لا يستطيع عميل قديم اعتماد تصميم أحدث، ولا يتجاوز الرابط المباشر تحقق الخادم.

## الحماية والحدود

عمليات حفظ الإجراءات والأدوار والحالات لا تعيد قراءة الدليل أو إحصاءات تقييماته؛ ليست هذه البيانات لازمة للقرار، بينما تستمر مصادقة المدير والتحقق من حالة المعاينة والمعاملة.

تبقى الكتابة في `medical_lab_workspaces` داخل Medical، مستقلة لكل مدير من هويته الخادمية. يعاد التحقق من إيقاف المعاينة داخل المعاملة، مع نسخة متوقعة ومعرف عملية ثابت ومنع تغيير نيتها. الطلب المتكرر لا يكرر الحالة أو الإسناد أو الإلغاء. الحقول الزائدة أو معرفات عضو أو حالات تأكيد حجز ترفض. قواعد Firestore المباشرة تبقى مغلقة.

حدود التجربة: 30 مسودة، و50 حالة، و10 أدوار، و10 خطوات و10 متطلبات للمسودة، و20 حدثًا محفوظًا لكل حالة، و40 معرف إعادة عملية. أضيف سقف 700000 بايت لحالة مساحة العمل قبل الكتابة، لحماية حد وثيقة Firestore مع النصوص العربية والنسخ المرجعية. لا حذف تلقائي لمسودة أو حالة لتفريغ المساحة. هذه حدود معمل وليست سياسة احتفاظ لخدمة أعضاء مستقبلية.

الحقل الحر مخصص للائحة أو المصدر أو قناة العمل؛ لا تدخل فيه بيانات أشخاص أو أسرار. منع مفاتيح بيانات الأعضاء لا يستطيع وحده اكتشاف كل معلومة شخصية يكتبها مدير داخل نص؛ يظل الالتزام بنطاق المحتوى مطلوبًا. لا توجد مرفقات في هذه النسخة.

## ما بقي خارج المعاينة

- شرح واعتماد لوائح الشركة والتحمل والاستثناءات وسلطات القرار ومسؤولي التشغيل والمهل والخصوصية والاحتفاظ قبل خدمات حقيقية.
- استقبال بلاغات الأعضاء وطلبات الموافقات والتحويلات وإشعار صاحب الطلب ما زال غير مفعل؛ هذه المسارات الحالية أمثلة إدارة.
- اتفاق أو API فعلي للمواعيد ورد الجهة والإلغاء قبل أي حجز مؤكد. لا تحاكي المنظومة وجود هذا الاتصال.
- اعتماد مواقع مقدمي الخدمة وإشعارات المتابعة وتقارير استخدام الأعضاء يحتاج تنفيذًا وتفعيلًا مستقلين.
- إثبات النسخ الاحتياطي والاستعادة والفوترة وTTL وربط نشر Google يحتاج حساب Google المخول؛ وجود أدوات التشغيل في المستودع لا يثبت تفعيلها.
- التعميم للأعضاء يظل موقوفًا حتى توجيه مستقل؛ لا يوفر هذا الإصدار زرًا ينشرها لهم.

## التشغيل والرجوع

يتطلب التحديث قدرة **`development-service-workflow-v1`** مع الواجهة 4.17.0. المصدر الوحيد للنشر Firebase `we-medical-dakahlia`، دون تعديل مشروع العضويات:

```bash
cd ~/cloudshell_open/Medical && git pull --ff-only origin main && bash scripts/deploy-medical.sh --existing-config
```

الفحص بعد النشر:

```bash
NODE_USE_ENV_PROXY=1 node scripts/check-live.mjs --require-service-workflow --require-roadmap-preview --require-visit-preview --require-directory-preview --require-development-lab --rayati --vercel
```

نشر Vercel وPages مختلف عن Firebase. عند غياب الخلفية المتوافقة تظل معاينات المدير المتوافقة متاحة، وتظهر رسالة تحديث للجزء الجديد. لم يُربط حساب Google بهذه الجلسة؛ يتبع إثبات الإتاحة فحص الإنتاج بعد النشر، ولا يستنتج من CI.

للرجوع: أوقف معاينة إجراءات الشركة من المعمل؛ تبقى البيانات واللقطات ولا ينفذ طلب جديد. يمكن العودة إلى واجهة وخدمة متوافقتين دون حذف بيانات، مع ملاحظة أن العميل الأقدم لا يراجع الحالات الجديدة؛ الأفضل الإيقاف حتى تثبيت نسخة متوافقة. لا يوجد تغيير في تجربة عضو يحتاج إرجاعه.


## دليل التحقق للإصدار

نجح محليًا **160 اختبار وحدة وحماية**، والبناء وفحص الأصول، ورحلة المتصفح الكاملة بعروض 320 و390 و768 و1440 دون أخطاء JavaScript. اختُبر السريان والقاهرة والمسودات القديمة والنسخ المرجعية والتعارض والإسناد والمتطلبات والإلغاء وإعادة الرد المفقود، وعزل العضو والزائر، وحجب المعاينة غير المتوافقة وحدها، وتصدير الأعداد دون النصوص الخاصة، والتنقل من لوحة المراحل والرجوع. نجح Firestore Emulator باستخدام SDK الفعلي، مع إلغاء متزامن مرة واحدة وعدم تغيير الدليل أو مصدر العضوية. الأدلة المحلية ببيانات مصطنعة في `/workspace/medical-deliverables/workflow-4170/`.
