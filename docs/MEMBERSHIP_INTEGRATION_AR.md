# تصميم ربط العضوية بين Medical وMyNekaba

**الحالة:** تصور تنفيذي بعد فحص الكود قراءة فقط، 17 أكتوبر 2026. لم يُنفذ ربط Firebase أو إنشاء قاعدة أو تغيير صلاحيات.

**تحديث التنفيذ:** أصبح كود الواجهة والخدمة والاختبارات متاحًا في المستودع، وفق نطاق الحقول الثلاثة والتقييم فقط. هذه الوثيقة تحفظ التصميم؛ راجع [تشغيل الخدمة والحالة الفعلية](BACKEND_SETUP_AR.md). لم تُهيأ بيانات اتصال الإنتاج أو تُنشر وظيفة Firebase بعد، وبقي MyNekaba دون تعديل.

**تحديث شرط الدخول:** الاطلاع على الدليل نفسه أصبح يتطلب جلسة متحققة على الخادم. يتيح نموذج العضو تذكّر جلسة الجهاز لمدة 30 يومًا دون حفظ مدخلات التحقق، مع إعادة التحقق عند الفتح وحذفها عند الخروج. الملفات العامة لا تتضمن نسخة بيانات تُحمّل قبل الدخول.

## نطاق الاستخدام المحدد من صاحب المشروع

- استضافة الواجهة على GitHub Pages: `https://abomawadda.github.io/Medical/`. تأكدت استجابته بـHTTP 200 يوم 17 أكتوبر 2026. تأجل Vercel، وليس شرطًا للتنفيذ.
- العضو يستعلم عن الجهات والخدمات، ويسجل تقييمه وملاحظاته على الزيارة فقط. لا يسجل طلب موافقة أو حجزًا أو ملفًا طبيًا أو بيانات أعضاء آخرين.
- نموذج الدخول يطلب كود الموظف ورقم الموبايل المسجل وآخر أربعة أرقام من الرقم القومي. لا إنشاء حساب عضو جديد أو كلمة مرور أو OTP أو إلزام باستخدام Firebase Auth للأعضاء ضمن النطاق الحالي.
- تطابق المدخلات الثلاثة يجري على خادم موثوق، ثم تصدر جلسة عضو محدودة الصلاحيات. حذف Firebase Auth من هذا المسار لا يلغي ضرورة التحقق الخادمي وحماية عمليات الكتابة.
- المدير هو المدير المعتمد في MyNekaba، ويضيف ويعدل ويحذف بيانات Medical. نموذج الأعضاء لا يمنح صلاحيات إدارة، حتى عند تطابق بيانات عضو يشغل منصبًا إداريًا.
- التصور القديم بإنشاء حسابات أعضاء تشغيلية واستخدام OTP واستضافة Vercel يستبدل بهذا النطاق. الأجزاء التالية تصف آلية العزل وفق هذه الحدود.

## الحكم

الاستفادة من سجل النقابة هي الاختيار الصحيح؛ لا نحتاج إنشاء سجل أعضاء موازٍ أو مطالبة الأعضاء بإعادة إدخال ملفاتهم. لكن بيانات العضوية ليست وحدها وسيلة إثبات هوية. يجب التمييز بين سجل العضو، وحساب الدخول، وصلاحيات استخدام Medical.

أوصي بمشروع بيانات مستقل لـMedical، مع قناة تحقق عضوية لا تكتب في مصدر MyNekaba، وهوية دخول طبية آمنة. إذا كان شرط «عدم التعرض» يشمل منع أي صلاحية اتصال جديدة بمشروع Firebase، فالمسار الممكن دون ذلك هو استيراد قائمة أهلية مختصرة من تصدير معتمد، وتحديثها دوريًا. الربط الحي لا يمكن ضمانه من دون وجود وصول مصرح به أصلًا أو إعداد وصول جديد.

## ما أكدته قراءة المصدر

المستودع المفحوص: `abomawadda/MyNekaba`، الالتزام `92dfbb9c8b8c9d144370d523e0f2fabcfd19b3c0`.

- شاشة الأعضاء تتعامل مع مجموعة `employees`؛ انظر `src/modules/employees/services/employeesService.js`.
- ملفات الأعضاء تتضمن حقولًا مثل `jobId` و`membershipId` و`memberState` و`membershipStatus` ووسائل التواصل.
- حسابات الدخول منفصلة في `user_accounts`، والربط يشمل `employeeId` و`firebaseUid` وحالة الحساب؛ انظر `api/_lib/trustedPrincipal.js`.
- الكود يدعم Firebase Auth وكذلك مسار حسابات قديمة؛ لا تثبت هذه القراءة أن كل عضو لديه حساب Auth فعال أو أن كل الحسابات migrated بالفعل.
- مسار `api/auth/verify-employee.js` ينشئ سجلات تسجيل وتدقيق، ومسار `api/auth/jit-session.js` قد يغير custom claims. لذلك ليست هذه واجهات تحقق «قراءة فقط» يمكن إعادة استخدامها تحت شرط منع الكتابة.
- قواعد Firestore الموجودة في المستودع لا تتيح سجل الأعضاء للعامة. لم أفحص نشر هذه القواعد أو إعدادات Firebase الإنتاجية أو بيانات أي عضو حقيقي.
- إعداد Firebase الاحتياطي في الكود مخصص للتطوير؛ لا يُعتبر إثباتًا لإعداد مشروع الإنتاج.

## حدود العزل

| المورد | التعامل المقترح |
|---|---|
| كود MyNekaba ونشره | لا تعديل ولا إعادة نشر |
| قواعد Firestore وStorage الحالية | لا تخفيف ولا نشر جديد |
| بيانات الأعضاء والحسابات وكلمات المرور | لا تعديل ولا ترحيل ولا إعادة تعيين |
| `custom claims` والجلسات الحالية | لا تغيير ولا نسخ جلسات المتصفح |
| مصدر أهلية العضو | قراءة معتمدة محدودة، أو تصدير مختصر إذا تعذر الوصول |
| أطباء ومستشفيات وفروع وخدمات وتقييمات | قاعدة مستقلة لـMedical |
| مدير Medical | نفس المدير المعتمد في MyNekaba، يربط بمعرف حسابه الثابت مع تحقق إداري خادمي؛ لا يعيّن عبر نموذج دخول العضو |

لا يوضع مفتاح إداري لـMyNekaba في Medical داخل المتصفح أو مستودع Git. ولا يُستخدم مفتاح واسع الصلاحية باعتباره ضمانًا لقراءة فقط؛ Firebase Admin SDK يتجاوز قواعد Firestore، ولذلك يجب أن تكون هوية الخدمة نفسها غير قادرة على الكتابة. كما لا أفترض أن دور IAM على مستوى قاعدة البيانات يقيّد القراءة تلقائيًا إلى حقول أو مجموعة واحدة؛ حدود القراءة الفعلية تحتاج مراجعة، ومعها وسيط خادمي محدود أو قائمة أهلية منفصلة إذا كانت الصلاحيات المتاحة أوسع من المطلوب.

## المسار المفضل إذا توفر وصول قراءة معتمد

1. **مشروع بيانات مستقل لـMedical**؛ Firebase خيار مناسب له، مع وظيفة خلفية مثل Cloud Functions. تستضاف الواجهة على GitHub Pages، ولا تُضاف مجموعات Medical إلى قاعدة MyNekaba. نشر الوظيفة الخلفية يتطلب الوصول والإعداد المناسبين في مشروع Medical؛ وجود GitHub Pages وحده لا يوفرها.
2. **طبقة تحقق خلفية داخل Medical** تستعلم عن سجل واحد مطابق لكود الموظف، وتقارن الهاتف كاملًا بعد تطبيعه وآخر أربع خانات من الهوية مع السجل نفسه. تُحوّل الأرقام العربية والفارسية والإنجليزية، وتُوحّد صيغة الهاتف دون مطابقة جزئية أو إسقاط الأصفار من كود الموظف. عند غياب السجل أو تعدده أو غياب حقل لازم يُرفض التحقق. يُمنع تنزيل قائمة الأعضاء إلى الواجهة أو البحث العام فيها أو إرجاع الرقم القومي والعناوين والبيانات المالية والمرفقات.
3. **مستوى التحقق** هو مطابقة بيانات ثابتة، وفق طلب صاحب المشروع، ولا يثبت ملكية الهاتف أو حصول الزيارة. تُحد المحاولات في مخزن مشترك تتحمله الوظائف المتعددة، وتُستخدم رسالة رفض عامة، ولا تُسجل المدخلات الحساسة في السجلات أو عناوين URL. لا يضاف OTP تلقائيًا لهذا النطاق، ولا توصف التقييمات بأنها زيارات مثبتة بمجرد المطابقة.
4. **الربط** بمعرف المصدر الثابت `employeeId` مع جهة الإصدار، لا بالاسم أو رقم الهاتف وحده. يمكن حفظ معرف مرجعي داخلي مشتق بدل كشف معرف المصدر في الصفحات العامة.
5. **قرار الأهلية** يبنى على سياسة متفق عليها لحقول العضوية الحالية. لا أعامل التقاعد أو حالة الاشتراك المالي أو تاريخًا مشتقًا تلقائيًا كسبب منع قبل تحديد سياسة الرعاية. ولا تعني العضوية وحدها ثبوت تغطية الأسرة أو خدمة طبية محددة.
6. **جلسة Medical مستقلة** وصلاحياته تطبق على خادمه. تُراجع الأهلية عند الدخول، وقبل الكتابات الحساسة وفق مدة صلاحية قصيرة محددة. لا تكون نسخة أهلية محلية قديمة تفويضًا مفتوحًا.

الحد الأدنى المخزن في Medical هو معرف الربط وحالة الأهلية وتاريخ التحقق ومعرف جلسة أو مستخدم داخلي محدود. لا يُنشأ سجل عضو موازٍ. الاسم الظاهر للتقييمات اختيار مستقل؛ الأفضل اسم مختصر أو عرض يحمي الخصوصية. لا ننسخ ملف العضو كله أو نحفظ مدخلات الدخول الثلاثة في التقييم.

ترسل الجلسة المحدودة مع طلب التقييم، وتستخرج الخدمة هوية الكاتب منها، وتتجاهل أي معرف عضو أو دور يرسله المتصفح. يكتب العضو تقييمه ويعدل ملاحظاته الخاصة، ولا يعدل تقييم غيره أو بيانات الجهات. التصفح دون اتصال يمكن أن يعرض بيانات الدليل المخزنة؛ لا يصدر جلسة ولا يسجل تقييمًا مركزيًا دون اتصال.

### صلاحية المدير

يثبت الخادم أن جلسة الإدارة تخص معرف المدير المعتمد من MyNekaba، وأن حسابه فعال وله دور الإدارة المطلوب. ويعيد التحقق قبل الإضافة والتعديل والحذف، بدل الوثوق بإظهار زر أو دور محفوظ في المتصفح. لا تُنسخ كلمة المرور أو تجزئتها من MyNekaba إلى الواجهة أو قاعدة Medical.

ربط نفس حساب الدخول يحتاج وسيلة تحقق متوافقة مع الحساب الحالي. يدعم المصدر حسابات قديمة وحسابات Firebase مرتبطة؛ لم يتم التحقق من وضع حساب المدير الإنتاجي أو إمكانية استعمال بيانات دخوله في تطبيق آخر. لذلك لا يُدّعى تنفيذ الدخول الموحد الآن، ولا تُستدعى مسارات JIT أو التسجيل التي قد تكتب في المصدر. إذا لم تتوافر وسيلة تحقق موجودة دون تغيير MyNekaba، يظل الربط الإداري بندًا مطلوب حسمه قبل تفعيل الإدارة العامة، مع بقاء المدير نفس الشخص المعتمد.

## بديل عدم الوصول إلى Firebase تمامًا

يستلم مسؤول Medical تصديرًا معتمدًا مختصرًا عبر وسيلة التصدير المتاحة أصلًا. في النموذج المطلوب يتضمن معرف العضو الثابت وحالة الأهلية وكود الموظف والهاتف وآخر أربعة أرقام فقط من الهوية، دون نقل الهوية الكاملة إلى Medical. يُنقّى الملف في بيئة موثوقة ثم يُستورد إلى مخزن تحقق خاص غير متاح للمستخدمين؛ لا يُنشر كـJSON أو JavaScript. ويمكن حفظ بصمات تحقق بمفتاح خادمي بدل القيم الأصلية حيث يناسب ذلك، دون اعتبار هذه البيانات كلمات مرور قوية.

هذا البديل لا يحتاج اتصال Medical بقاعدة MyNekaba ولا تعديل كودها أو قواعدها. لكنه ينشئ نسخة محدودة تحتاج حماية وتحديثًا، ولا يعكس تغييرات العضوية لحظيًا. يجب تحديد مسؤول التصدير، وفترة التحديث والصلاحية، وآلية إيقاف عضو. ولا أفترض أن شاشة التصدير الحالية تنتج هذا الشكل دون فحص؛ يمكن تنقية تصديرها الموجود خارج المشروع الأصلي.

## الدخول الموحد ليس مضمونًا من دون نقطة ربط

جلسة MyNekaba في متصفحه لا تنتقل تلقائيًا إلى نطاق Medical. الدخول الموحد الحقيقي يحتاج بروتوكولًا أو نقطة تسليم هوية موثوقة، أو مزود هوية مشتركًا صالحًا لذلك. نسخ `localStorage` أو تمرير JWT طويل العمر في رابط ليست طريقة مقبولة. إذا لم توجد نقطة ربط جاهزة، نبدأ بدخول Medical المستقل مع أهلية الأعضاء، ونؤجل SSO بدل تعديل MyNekaba ضمن هذا النطاق.

## بيانات Medical المقترحة

- `providers`: الطبيب أو المؤسسة ونوعها وتخصصاتها.
- `branches`: مقار العمل وأرقام التواصل والعناوين والمواعيد والخرائط.
- `services` و`contracts`: خدمات الفرع، ومصدر الاعتماد، وفئة المستفيد، وبداية الصلاحية ونهايتها.
- `reviews`: معرف عضو Medical ومعرف الجهة/الفرع والتقييم وتاريخ النشر وحالة المراجعة. لا نضع تقييمات أو أعدادًا افتراضية، ولا نصف الزيارة بأنها موثقة لمجرد تسجيل الدخول.
- `audit_logs`: سجل تغييرات المدير داخل Medical. المقترحات العامة والحجز والموافقات وملفات المرضى خارج النطاق الحالي؛ ملاحظات العضو مرتبطة بتقييم زيارته فقط.

تُرحّل بيانات الدليل الحالية بعد تنظيفها، مع الحفاظ على المعرّفات أو إعداد خريطة انتقال. تُراجع التغطية بدل نقل `both` العام باعتباره حقيقة. المفضلة العامة يمكن أن تبقى محلية، أو تتزامن لحساب العضو حسب الحاجة.

## ترتيب التنفيذ ومعايير القبول

1. اعتماد GitHub Pages للواجهة وتأجيل Vercel. يجب أن ينشر إعداد Pages ملفات التطبيق فقط؛ إعداد المصدر الحالي ينشر جذر `main`، ولا يعتمد تلقائيًا مجلد `dist` الذي جهز لـVercel.
2. توفير وصول قراءة معتمد أو تصدير مختصر لمطابقة المدخلات الثلاثة، وحسم وسيلة التحقق من المدير الحالي دون تعديل MyNekaba.
3. إنشاء قاعدة Medical ووظيفة التحقق وحفظ التقييمات، ثم تنظيف بيانات الجهات وبناء عمليات الإدارة الخادمية. يُقيد CORS بأصل GitHub Pages المسموح؛ مسار `/Medical/` ليس حد صلاحيات، وCORS ليس بديلًا للجلسة.
4. بناء واختبار موصل العضوية والتقييمات في بيئة اختبار، ثم نشر الواجهة والوظائف والتحقق من عملها من جهازين.

قبل الإطلاق يجب إثبات: عضو تتطابق بياناته الثلاث يدخل، والخطأ في أي منها يُرفض، وتعارض المطابقة يُرفض، وتوقف المصدر لا يتجاوز التحقق، والمحاولات محدودة على الخادم، والمستخدم لا يستطيع قراءة ملفات أعضاء آخرين أو تعديل الدليل، وتقييمه مربوط بهويته الخادمية، وصلاحية إدارة Medical لا تأتي من تعديل المتصفح أو نموذج العضو. يجب أن يظهر تقييم أُرسل من جهاز لدى الإدارة على جهاز آخر. وبالنسبة لمسار القراءة المباشرة، يجب فشل الكتابة إلى المصدر باختبارات صلاحيات في بيئة اختبار أو عبر محاكي؛ لا نختبر منع الكتابة بمحاولة تعديل بيانات إنتاج حقيقية.

**حالة هذا التغيير:** تجهيز نشر Medical وتوثيق التصميم فقط. نسخة MyNekaba المحلية للفحص بقيت دون تعديلات، ولم تُنفذ أي طلبات كتابة أو دخول أو تسجيل أو تغيير صلاحيات في Firebase الخاص به.
