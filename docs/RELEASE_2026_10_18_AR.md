# إصدار بطاقة العضو ومراجعة نسخ التقييمات

## الحالة الصريحة

الكود واختباراته جاهزان في هذا الإصدار. تُنشر الواجهة من GitHub Pages بعد دفع التعديلات. نشر وظيفة Firebase الجديدة يحتاج جلسة المالك المعتمدة في Cloud Shell؛ جلسة المساعد لا تحتوي اعتماد Google للنشر، ولا يكفي اتصال GitHub لتغيير وظيفة الإنتاج. لم يُغيّر هذا الإصدار مصدر MyNekaba أو قواعده أو حساباته.

لا نعتبر تفعيل الإصدار على الإنتاج مكتملًا إلا بعد أن يعلن عنوان الصحة العام دعم `member-profile` و`review-revisions` ثم تجربة المالك. حتى ذلك الوقت يعرض الموقع الجديد بطاقة العضو كخدمة تنتظر التفعيل ويمنع قرارات المراجعة على الخدمة القديمة، بينما يبقى دخول العضوية والدليل والتقييمات القائمة متاحة.

## السلوك بعد تفعيل الوظيفة

- ترحيب باسم العضو، والضغط عليه يفتح بياناته وتقييماته.
- بطاقة: الاسم، كود الموظف، رقم العضوية النقابية، الوظيفة، مكان العمل، آخر تسجيل دخول إلى Medical والدخول السابق بتوقيت القاهرة. الحقل المفقود يظل واضحًا ولا يُخمن.
- التقييم المنشور يخرج من طابور انتظار الاعتماد، ويظهر في «تمت مراجعتها».
- الاعتماد الناجح يغلق النافذة ويعرض إشعارًا مؤقتًا، ولا يعيد فتحها تلقائيًا.
- النسخة تُراجع مرة واحدة. إعادة إرسال الطلب نفسه لا تعيد الكتابة ولا تضاعف النجوم أو التدقيق.
- يستطيع المدير إخفاء المنشور، لكنه لا يعيد اعتماد النسخة نفسها بعد إخفائها. العضو وحده يعدل محتواها لتصبح نسخة جديدة معلقة.
- نموذج تعديل التقييم موجود في صفحة العضو ويعرض قيمه السابقة. حفظ المحتوى نفسه لا يفتح مراجعة جديدة.
- إذا تغيرت النسخة أثناء انتظار قرار المدير يرفض الخادم القرار القديم؛ يجب تحديث القائمة ومراجعة التعديل.
- بيانات البطاقة لا تُرسل للآخرين ولا تُحفظ في تخزين المتصفح. نشاط الدخول يُكتب في Medical فقط.

## التحقق المنفذ

نجحت 38 تجربة للخادم، واختبارات متصفح Chromium للدخول والبطاقة وتعديل العضو وطابور القرارات وإغلاق النافذة وعدم تكرار الاعتماد، واختبار محاكي Firestore للمعاملات الفعلية. يتضمن اختبار المحاكي طلبَي اعتماد متزامنين: ينفذ التغيير مرة واحدة، ولا يتكرر سجل التدقيق، ويُرفض قرار على نسخة عدّلها العضو. بيانات الاختبارات مصطنعة، ولا تستخدم سجلات إنتاج أو مفاتيح أعضاء حقيقية.

## تفعيل الخلفية بأمر واحد

في الطرفية نفسها التي استخدمها المالك للنشر السابق:

```bash
cd ~/cloudshell_open/Medical && git pull --ff-only && bash scripts/deploy-medical.sh --existing-config
```

يقرأ الأمر إعداد Medical الخاص الموجود من النشر السابق، ويختبر الوظيفة وينشرها وقواعد Medical فقط، ثم يفحص قدرات عنوان API المنشور. لا يقرأ قيم أسرار Secret Manager إلى الطرفية، ولا يرسل مفاتيح في المحادثة، ولا ينشر أي شيء إلى `nekaba2026`.

إذا طلب Firebase تسجيل الدخول، استعمل الأمر المعتمد سابقًا `npx --yes firebase-tools@15.34.0 login --no-localhost`، وأكمل التفويض في المتصفح؛ رمز التفويض يبقى في طرفية المالك. إذا لم يوجد ملف إعداد Medical، ارجع إلى تعليمات BACKEND_SETUP_AR واستعمل معرف حساب المدير ومفتاح Web API العام المعروفين للمالك.

## تحقق القبول

1. افتح إصدار الموقع الجديد وحدّث التطبيق إن ظهر زر التحديث.
2. ادخل بعضو؛ يظهر اسمه، والضغط عليه يعرض بطاقة بياناته فقط.
3. تحقق من أن كود الموظف ورقم العضوية حقلا عرض مختلفان، ومن أن الحقول الناقصة واضحة.
4. سجل الخروج والدخول مرة أخرى؛ يتقدم آخر الدخول ويصبح السابق هو الدخول الذي قبله. التحديث أو استعادة التذكر لا يحسبان دخولًا جديدًا.
5. احفظ تقييمًا؛ يراه المدير في الانتظار. اعتمده؛ تغلق النافذة ويخرج من الانتظار وتظهر النجوم للعضو.
6. افتح سجل ما تمت مراجعته؛ لا يوجد زر لإعادة الاعتماد لنفس النسخة.
7. أخف التقييم؛ لا يُتاح نشره ثانية دون تعديل صاحبه. عدّل محتواه من حساب العضو؛ تظهر نسخة جديدة في الانتظار.
8. على جهازين، عدّل العضو أثناء فتح المدير نسخة قديمة؛ لا يعتمد القرار القديم المحتوى الجديد.
9. تأكد من عدم حفظ الاسم أو الوظيفة أو الهاتف أو الهوية في تخزين الجلسة المحلي؛ المخزن يحتوي رمز الجلسة وعنوان API والانتهاء فقط.
