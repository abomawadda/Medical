# استقرار التشغيل وجودة بيانات الدليل — المرحلة الأولى

## الحالة الفعلية

نُفذ تدقيق محلي ولوحة للمدير من «جودة بيانات الدليل»، بمرشحات القسم ونوع الملاحظة وتنزيل تقرير وفتح السجل للتصحيح. تتحدث النتيجة عند إعادة فتح اللوحة بعد الحفظ. التقرير يعالج بيانات الجهات الحالية فقط، ولا يضم بطاقات الأعضاء أو تعليقات التقييمات أو رموز الجلسات. لا يعتمد التدقيق على خدمات خارجية ولا يرسل بياناتها إليها.

الفحص آلي للاكتمال والاتساق؛ لا يثبت صحة الرقم أو التعاقد. لا يحذف التكرارات، ولا يحول المعلومات الناقصة إلى معلومات موثقة. يشترط تشابه الاسم والتخصص والمستشفى والعنوان لاقتراح تكرار، ولا يعتبر تعدد الفروع أو مشاركة رقم الاستقبال تكرارًا وحدهما. يحمي المعرّف المفقود أو المكرر من فتح تعديل قد يصيب سجلًا آخر.

خط الأساس بتاريخ 18 أكتوبر 2026، من بيانات الدليل الأصلية في المستودع: 230 سجلًا (169 مقر طبيب/قسم و3 مستشفيات و24 مرفقًا و34 سجل طوارئ). منها 40 بلا رقم قابل للاستخدام وفق فحص الصيغة، و230 بلا رابط مصدر HTTPS، و196 بلا تاريخ تحقق. التغطية أو بيانات الطوارئ لم تُؤكد في هذه السجلات. هذا إجمالي سجلات، وليس عدد أشخاص أو جهات فريدة؛ قد توجد سجلات مركزيّة أو فروع صحيحة. استثناء نشرات التعليمات مقصود: تحتاج مراجعة محتوى وإجراءات مختلفة.

يمكن إعادة الفحص دون تغيير الملفات:

```sh
npm run audit:catalog
npm run audit:catalog -- --report /tmp/medical-quality.json
```

القائمة داخل لوحة المدير تفحص الدليل المركزي بما فيه التعديلات المحفوظة. أمر الطرفية يفحص نسخة المستودع فقط؛ لا يفترض تطابقها مع بيانات الإدارة المركزية.

## ترتيب تصحيح البيانات

1. أرقام الطوارئ والاتصال الناقصة: تأكيد الجهة صاحبة الرقم وصلاحيته ومواعيد استقباله، لا استبداله بتخمين أو رقم شخصي.
2. إضافة رابط مصدر معتمد وتاريخ تحقق حقيقي. التاريخ الحالي وحده ليس دليل تحقق.
3. تأكيد التغطية حسب الفرع والخدمة؛ تبقى «تحتاج تأكيدًا» حتى وجود المصدر والتاريخ. لا نستنتج الاستحقاق من الوظيفة أو حالة العضوية.
4. معالجة المعرّفات والتكرارات المحتملة بمراجعة بشرية، مع الحفاظ على معرّفات الجهات والتقييمات المرتبطة بها.
5. إعادة مراجعة المعلومات التي مضى على تحققها 180 يومًا. هذه عتبة تنظيمية للمراجعة، وليست تاريخ انتهاء التعاقد.

## تنظيف السجلات والنسخ الاحتياطي

جُهز `scripts/medical-operations.mjs` باستخدام واجهة Firestore Admin الرسمية. يرفض أي مشروع غير `we-medical-dakahlia` ويتأكد من هوية قاعدة `(default)` ونوعها وموقع `europe-west1` قبل أي تعديل. لا يقرأ مستندات أعضاء أو مراجعات، ولا يتعامل مع IAM أو أسرار أو مشروع النقابة. لا يحتاج تغيير كود وظيفة Firebase أو إعادة نشرها.

الأوضاع:

- `plan`: يعرض المقصود فقط، دون اتصال أو مصادقة.
- `status`: يقرأ إعداد TTL وجدول النسخ وبيانات النسخ المكتملة فقط؛ لا يغير الإعدادات.
- `apply`: يطلب TTL على `expiresAt` لمجموعتي `medical_sessions` و`medical_limits`، وينشئ جدول نسخة يومية باحتفاظ سبعة أيام إذا لم يوجد جدول يومي. يحافظ على أي جدول قائم ولا ينقص مدة احتفاظه. ثم يعرض الحالة الفعلية؛ `requested: true` لا تعني أن TTL أصبح `ACTIVE`.

الأمر الجاهز من جلسة Cloud Shell الخاصة بالمالك، بعد تحديث المستودع:

```sh
cd ~/cloudshell_open/Medical
git pull --ff-only
node scripts/medical-operations.mjs plan --project we-medical-dakahlia
node scripts/medical-operations.mjs status --project we-medical-dakahlia
node scripts/medical-operations.mjs apply --project we-medical-dakahlia
```

المصادقة من `gcloud auth print-access-token` داخل ذاكرة العملية فقط؛ لا يُنسخ الرمز للمحادثة أو ملف أو معاملات الأمر. إذا لم تكن الجلسة مصرحًا لها، يسجل المالك الدخول داخل Cloud Shell نفسه. تعالج صلاحية Firestore المحددة عند الحاجة، دون منح Owner/Editor كحل عام. قد يلزم إذن قراءة بيانات النسخ حتى لعرض الحالة.

TTL لا ينفذ حذفًا لحظيًا. انتهاء الجلسات وحدود المحاولات مطبق في الخدمة مسبقًا ولو تأخر التنظيف. لا تطبق سياسة الحذف على التقييمات أو التدقيق أو نشاط العضو في هذه الحزمة. الاحتفاظ بتلك البيانات قرار لاحق يُوثق مع المالك قبل أي حذف.

قد تنجح خطوة وتفشل التالية بسبب الصلاحيات؛ لا توجد معاملة واحدة تجمع إعدادات Google. عند الفشل يُعاد `status` لمعرفة ما تغير، ثم يُعالج السبب وتُعاد الأداة. إعادة التشغيل تحافظ على TTL الفعال أو الجاري إنشاؤه وعلى الجدول اليومي الموجود.

نسخ Firestore تحفظ قاعدة Medical الخاصة كاملة، بما فيها المراجعات وسجل التدقيق؛ لا تنشر ملفاتها في GitHub ولا على رابط عام. قد تُحتفظ بيانات الجلسات المحذوفة داخل نسخة سابقة حتى انقضاء احتفاظها؛ استعادتها لا تعيد صلاحية جلسة انتهت بحسب وقت الخادم. لا تتضمن النسخة إعدادات IAM أو Secret Manager أو كود الخدمة أو مشروع النقابة؛ تلك ليست بديلًا عن سجل إصدارات الكود وإدارة الأسرار.

النسخ المخزنة واستعادتها وحذف TTL قد تكون لها تكلفة على Blaze. جدول يومي بسبعة أيام اقتراح تشغيل ابتدائي محدود، وليس حد إنفاق أو تقديرًا مضمونًا. تنبيهات الميزانية ليست سقفًا يمنع الإنفاق؛ يلزم تفعيلها من حساب الفوترة ومراجعة قراءات المصدر أيضًا. لم تُفعّل الفوترة أو التنبيهات أو الجدول أو TTL من جلسة المساعد، لعدم وجود هوية Google متصلة.

## إثبات النسخ واختبار الاستعادة

إنشاء الجدول لا ينشئ سبع نسخ فورًا. بعد موعد التنفيذ يعاد `status` ويجب ظهور نسخة `READY` تعود لقاعدة Medical؛ الصفر يعني أن وجود نسخة مكتملة لم يُثبت بعد.

قبل إعلان O04 مكتملًا، تُنفذ تجربة استعادة مُدارة إلى قاعدة مستقلة جديدة مثل `medical-restore-check-20261018` في مشروع Medical نفسه، دون استبدال `(default)` أو تحويل الواجهة أو الخدمة إليها. من صفحة Firestore Backups يختار المالك نسخة `READY` التابعة لـMedical ويستعيدها إلى الاسم الجديد. تراجع صلاحيات قاعدة الاختبار وقواعد منع الوصول العام قبل اختبارها بهوية مشغّل محدودة؛ لا تُربط بالمتصفح أو مصدر العضويات.

معايير التجربة:

1. تسجيل وقت النسخة وبدء وانتهاء الاستعادة وحالة العملية دون محتويات شخصية.
2. فحص معرّفات عينة جهات وتعديلات الإدارة وحالات وإصدارات مراجعات مختارة على الخادم الخاص فقط. لا تُنسخ التعليقات أو بيانات الأعضاء إلى تقرير عام.
3. مقارنة المجاميع مع المراجعات المنشورة، والتحقق من أن رمزًا منتهيًا لا يصبح صالحًا بسبب الاستعادة. لا تسجل دخولًا حقيقيًا أو تكتب إلى MyNekaba لغرض التجربة.
4. تسجيل حدود الفقد المقبول من زمن النسخة الفعلية وزمن الاستعادة المقاس. «نسخة يومية» لا تضمن وحدها حد فقد 24 ساعة إذا فشل الجدول.
5. بعد نجاح الفحص، حذف قاعدة التجربة من حساب المالك وإنهاء تكلفتها. لا يحذف هذا السكربت قواعد بيانات أو نسخًا احتياطية تلقائيًا.

هذه تجربة خارجية لم تنفذ بعد؛ اختبارات الكود الاصطناعية تثبت حواجز المشروع وسلوك الأداة وإعادة تشغيلها، ولا تثبت استعادة نسخة Google فعلية. يظل البند جزئيًا حتى توثيق النتيجة.
